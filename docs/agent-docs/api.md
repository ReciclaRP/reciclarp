# API reference (`api/`)

Everything relevant is in one file: `api/src/server.js` (~1,190 lines). The DB
schema and seed data live in `api/src/db/schema.js`.

## Running

```bash
cd api && npm install && npm run dev   # node --watch src/server.js
cd api && npm test                     # node --test
```

Environment variables (also read from `api/.env` via dotenv):

| Variable | Default | Purpose |
| --- | --- | --- |
| `RECICLA_API_PORT` | `3000` | Listen port. |
| `RECICLA_RESEND_SECRET` | unset | Resend API key. **Unset = guest mode**: OTC codes go to the pino log instead of email. |
| `RECICLA_WEBAPP_URL` | `http://localhost:5173` | Allowed CORS origin. |
| `RECICLA_ADMIN_EMAIL` | `test@example.com` | Email of the seeded admin (id 0, `ong=1`, `validated=1`). The test harness overrides it to `admin@example.com`. |
| `RECICLA_ESCALATION_TOKEN` | autogenerated + logged at INFO | Redeemed by `/auth/special` to promote an account to ONG. |
| `RECICLA_OTC_DURATION` | `15` | Minutes an OTC code stays valid before `Tickets.purge()`. |
| `RECICLA_MAX_POINTDESCRIPTION_LEN` | `200` | Character cap applied to point descriptions before XSS filtering. |

To watch availability, `../scripts/ping-watch.sh` polls `GET /api/ping` and
reports outages (optionally by SMS); see [`scripts.md`](scripts.md).

The SQLite file is `recicladb.sqlite` in the process working directory. When it
does not exist at boot, the schema is created and seeded with the admin account
and 8 real "ecopontos" from Ribeirão Preto (seed data in
`api/src/db/schema.js`). An existing file is never reseeded.

## Cross-cutting behavior

- **Response envelope:** `{ type: "okay" | "error", description?, ... }` for
  JSON routes. Exceptions: `POST /point/list` returns a bare array of rows, and
  `GET /api/ping` returns the client IP as plain text.
- **All routes POST** except `GET /api/ping` (health check).
- **CORS** restricted to `RECICLA_WEBAPP_URL`.
- **Rate limits** (express-rate-limit):
  - global: 100 req / 15 min per IP (`ipv6Subnet: 56`);
  - `/auth/login`, `/point/create`, `/point/update`: **1 req / 2 min per IP**
    (`ipv6Subnet: 48`);
  - `/auth/token`: **1 req / 1 min per IP**.
  - These will block repeated manual testing; restart the API or vary the source
    address.
- Auth on protected routes is checked per-handler (no middleware): the handler
  constructs `Account(email)` and compares `account.token_read() === token`
  (or `token_list.get(email) === token`) with strict equality. ONG-only routes
  additionally call `is_ong()`.
- Validation uses a module-level `EMAIL_REGEX`. Point descriptions are passed
  through `xss.filterXSS` and capped with `MAX_POINTDESCRIPTION_LEN`; material
  flags go through `bton()` (only `true` becomes `1`). Coordinates and time
  fields are **not** validated yet (see `security.md`, SEC-007).

## Routes

| Route | Auth | Purpose |
| --- | --- | --- |
| `POST /auth/login` | — | Send an OTC code to an existing, non-banned email. |
| `POST /auth/token` | — | Exchange email + OTC code for a token. |
| `POST /auth/check` | token | Return `{ email, name, id, banned, ong }` if the token is valid. |
| `POST /auth/delete` | token | Anonymise the caller's account (fails if banned). |
| `POST /auth/logout` | token | Invalidate the caller's in-memory token. |
| `POST /auth/special` | token + code | Promote the caller to ONG when `code` matches `RECICLA_ESCALATION_TOKEN`. |
| `POST /point/list` | — | Return **all** points (including `approved=0`) as a bare array. |
| `POST /point/create` | token | Create a point. Citizens get `approved=0`; ONG accounts are auto-approved. |
| `POST /point/update` | ONG | Update a point; also sets `approved=1` and preserves `creator`. |
| `POST /point/remove` | ONG | Delete a point. |
| `POST /point/approve` | ONG | Set `approved=1` on a pending point. |
| `POST /point/access/log` | token | Record an access (`{ pid }` at the body root) for the authenticated user. |
| `POST /point/access/get` | ONG | Return up to `no` access rows for `{ pid }`, newest first. |
| `POST /point/access/no` | ONG | Return the access count for `{ pid }` as `{ type: "okay", data }`. |
| `POST /report/create` | token | File a citizen report about a point (`{ description, problem_kind, pid }`). |
| `GET /api/ping` | — | Health check; returns `req.ip`. |

Body shapes worth remembering:

- Point create/update: all fields live under `data` — `pointdescription`,
  `lati`, `long`, `time_open`, `time_close`, `accepts_paper`,
  `accepts_metal`, `accepts_organic`, `accepts_biological` (update also needs
  `data.pid`). Flags at the body root are ignored.
- Approve/remove: `{ data: { pid } }`.
- Access log/no: `{ pid }` at the root. Access get: `{ pid, no }` at the root.
- Report create: `{ description, problem_kind, pid }` at the root.

## Data model

`api/src/db/schema.js` defines four tables:

- `user` — `id`, `uname`, `email` (unique), `banned`, `validated`, `ong`.
- `point` — `pid`, `pointdescription`, `lati`/`long`, `time_open`/`time_close`
  (TEXT, e.g. `"7:00"`), four `accepts_*` flags, `approved`, `creator`.
- `report` — `rid`, `reportdescription`, three `category_*` flags, `uid`, `pid`.
- `access` — `aid`, `hour_accessed` (TEXT `HH:MM`), `uid`, `pid`.

Foreign keys are declared but SQLite enforcement is off by default (SEC-011).

## Key classes (server.js)

- `Tickets` — in-memory email → **six-digit** OTC code map with creation times;
  `purge()` expires codes after `RECICLA_OTC_DURATION`, `get()` is one-shot.
- `Tokens` — in-memory email → random token map (`token_list`), with
  `invalidate`.
- `Account` — wraps a user row by email; methods include `exists()`,
  `__is_banned()`, `__is_validated()`, `is_ong()`, `send_loginmail()`, `ban()`,
  `token()`, `token_read()`, `logout()`, `make_ong()`, `delete()`,
  `get_id/get_email/get_name`. Constructing it auto-creates a valid-looking
  email that does not exist yet.
- `Point` — `read_from_pid`, `new`, `update` (approves and preserves creator),
  `log_access(uid)`, `times_accessed()`, `get_accesses(n)` (clamped 1–1000,
  newest first), `approve()`, `delete()`.
- Helpers `bton(b)` (booleans → SQLite 0/1), `get_point_list()`, and
  `create_report(description, problem_kind, uid, pid)`.

## Adding a route

1. Match the existing handler shape: log with `logger.info`, validate body
   fields first and return the `type: "error"` envelope on malformed input.
2. Reuse `Account`/`Point` for auth and data access; do not introduce middleware
   silently.
3. If a new limiter is needed, follow the pattern of `points_limiter`.
4. Add integration coverage under `api/tests/` (see `testing.md`).
5. Update this file's route table in the same change.
